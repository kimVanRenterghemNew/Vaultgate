The idea and the threats

An agent that holds a key can leak it: a prompt injection in a web page or an email, a key that ends up in a log or a reply, a plugin that is not what it says. Once a key has been in a model’s context, treat it as leaked.

With Vaultgate the agent holds a placeholder, such as {{secret:github_token}}, and a virtual key that works nowhere else. The real value exists in the Vaultgate process only while it fills in one request.

Designed against

  • A compromised agent: prompt injection, a poisoned repository, a hostile plugin.
  • Tools that write keys to logs or telemetry.
  • Someone in the middle: a rogue proxy, a captive portal, an inspection root you never trusted.
  • A stolen disk or backup while the vault is locked.
  • Other programs running as you that click buttons or call the local ports.

Not designed against

  • Malware that reads memory while the vault is open, a kernel rootkit or a compromised operating system.
  • Physical attacks on a security key, or probing the RAM of a running machine.

Closed by default

Every request runs down one decision table. The first rule that matches decides, and its name goes into the response (x-vault-gate-rule) and into the encrypted log. A refusal happens before the secret is decrypted.

The table is data, not a tangle of if-statements, and every rule has a test with a request it must refuse.

Keys inside keys

Vaultgate uses libsodium and nothing of its own. Values are sealed with XChaCha20-Poly1305; keyed hashes use BLAKE2b.

Each passkey derives its own key with the WebAuthn PRF extension
that unwraps one copy of the vault key: 32 random bytes, never derived from a password
which wraps a separate record key for each secret, grant and log line
which encrypts each field on its own, bound to its record and position

Binding each field to its record and position (as associated data) means a ciphertext cannot be moved from a name into a value without failing to decrypt. Remove a passkey and its wrapped copy is gone; nothing else is re-encrypted.

A vault from before passkeys may still have a passphrase; that copy is wrapped with a key from Argon2id.

Nothing readable on disk

A stolen laptop or backup gives an attacker files, not information. Even which tool used which secret, and when, is encrypted.

OpenEncrypted, field by field
format versionsecret names, values and domains
key-derivation settings and saltstools and their settings
the wrapped vault keysgrants and approvals
random record idssettings, and the log, line by line

Virtual keys are stored only as a keyed hash. A keyed MAC over the header and a manifest of record versions stops a rollback: put back an older copy of one record and the vault refuses to open.

When the vault opens, Vaultgate also checks its own installed files against the hashes the vault recorded last time. A changed file keeps the vault closed until you confirm the change.

Secrets in memory

Keys live in libsodium’s guarded memory (locked pages with guard pages) and are wiped after use where the library allows it. The vault locks itself after a while without use, 15 minutes by default.

Honest limit: a value that passes through JavaScript as a string cannot be wiped. Malware running as you while the vault is open can read memory. Vaultgate keeps that window small and says so.

The log comes first

Every decision is written to the encrypted log before the secret is decrypted. Cannot write the log? Then nothing goes out (audit-unavailable). After three failures in a row, the vault locks itself. No secret value is ever written to the log.

A touch, not a click

A program can click a button. It cannot touch your passkey. Anything that gives more than one request asks for a WebAuthn assertion with user verification: a grant, a new domain or place for a secret, turning Sensitive off, rotating a secret, creating or rotating a virtual key, a new passkey, trusting a certificate root.

Taking rights away (revoking, blocking, untrusting) never needs a touch.

The real site

Vaultgate trusts what Node and Mozilla trust, strictly, and remembers the chain it first saw for each site. The check runs during the TLS handshake, before a byte of the request leaves.

  • A renewed certificate under the same root: fine.
  • A root you trusted on purpose, such as your company’s inspection proxy: fine, and each request it handles is marked as inspected.
  • Any other new root: stopped (tls-chain-changed or tls-untrusted) until you decide. That is what someone in the middle looks like.

Scrubbing the reply

If a service echoes the key back, the reply is cleaned before the agent sees it: as plain text, base64 in every alignment, base64url, hex, URL-encoded and in JSON, also when it is split across two chunks. Streaming is not slowed down: only the tail that could start a match is held back.

Pairing a tool

A tool asks for its key with a device flow (RFC 8628). Its terminal shows a short code; you check it in the portal and touch your passkey; the tool fetches its key once. The key never appears on a screen, a clipboard or in a chat.

A request expires after 10 minutes, at most five wait per address, and the device code is kept only as a hash. Paired keys rotate: an old key offered again is treated as stolen (key-reuse-detected) and the tool is revoked.

Wrong keys are slowed down: after repeated failures an address stops getting answers for a while, longer each time.

The portal itself

  • It listens on loopback only, and refuses any other host name (status 421), so a web page cannot reach it through DNS rebinding.
  • Sign-in is a passkey. A strict content security policy with a fresh nonce per page; no external scripts, styles or fonts.
  • It opens in its own browser window without extensions, so an add-on cannot read what you type.
  • A secret value goes in once and no page or API returns it.

Architecture

Small modules with one job each, wired in one place. Decisions are tables, state changes are pure functions with effects as data, and every module gets its dependencies passed in: no hidden globals.

ModuleJob
cryptolibsodium primitives, guarded memory
vaultthe key hierarchy, field encryption, locking, rollback and code checks
registrysecrets, tools, grants and settings; never returns a value
policyvirtual keys, domains, places in the request, the decision table
approvalasking in the tray, with a timeout
proxyforward and reverse routes, filling in, streaming
scrubcleaning replies across chunk boundaries
auditthe encrypted log, written first
tlsthe chain checks
devicepairing with a device flow
portal, window, touchthe portal, its own window, the passkey touch
tray-linkthe link to the tray, with a one-time token

Tests enforce the structure: modules import each other only through their public index, files stay small, and every journey test ends by searching all output for the fake secrets it used.

What it protects against, and what not

ThreatWhat Vaultgate does
An agent or plugin reads your keyIt never has one: placeholders only.
A prompt injection sends the key elsewhereA domain per secret; a new tool, secret and domain asks you first.
The API echoes the key backThe reply is scrubbed, in every common encoding.
Stolen disk or backupEverything is encrypted; without a passkey it is useless.
A stolen virtual keyWorks only through Vaultgate, from allowed addresses, for what was granted. Revoke it in one click.
A program clicks AllowAnything that lasts asks for a touch of your passkey.
Someone in the middleA new root you do not trust stops the request.
Malware reading memory while the vault is openNot covered. Auto-lock and wiped buffers keep the window small.

The attack bench

npm run attack starts the real process with fake secrets and runs every attack. The attacks come from security reviews and one question: if you were an agent on this computer, how would you get in?

Open, with the reason

  • Reading another tool’s key file and posing as that tool. On Windows the file is protected against other accounts, not against a program running as you. macOS and Linux follow.
  • Changing the installed files. The vault notices when it opens; a signed release and an install folder you cannot write to come with the release.
  • Reading the memory of an open vault. See secrets in memory.
