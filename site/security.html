Security Architecture & Technical Threat Model

A complete reference for developers, security auditors, and code reviewers: Hexagonal architecture, zero plaintext at rest (Libsodium XChaCha20-Poly1305), hardware proof-of-presence (FIDO2 PRF), fail-closed decision rules, Ed25519 code integrity, and real-time response scrubbing.

1. The Core Paradigm: Secret Mediation without Exposure

Traditional credential managers assume the client executing code must receive the raw API key to function. For AI agents, this paradigm is fundamentally broken.

The Broken Legacy Paradigm

The agent or plugin receives the real key in memory or prompt context. A single prompt injection from a scraped webpage, a hostile repo commit, or a compromised dependency tricks the model into leaking the key in a prompt, writing it to terminal logs, or sending it to an attacker's domain.

The Vaultgate Paradigm

The agent only ever receives an opaque placeholder ({{secret:github_token}}) and a localized virtual key (x-vault-gate-tool-key: vg_…). Vaultgate injects the real key directly into outbound TCP packets at the very moment the request leaves your computer, strictly verifying destination domain, header location, and user authorization first.

Threat Model & Adversary Assumptions

In Scope for Defense

  • Compromised AI Agent: Prompt injection, jailbreaks, poisoned repositories, or malicious plugin dependencies.
  • Untrusted / Buggy Tools: Scripts writing environment variables or payloads to telemetry or log files.
  • Network Intermediaries (MitM): Rogue proxies, Wi-Fi captive portals, or untrusted corporate inspection CAs.
  • Stolen Backup / Disk Image: Offline access to the user's hard drive while the vault is locked.
  • Local User-Level Scripts: Processes executing under the same user account attempting synthetic clicks or socket sniffing.

Out of Scope

  • Kernel-level rootkits, hypervisor compromises, or OS-level Ring 0 keyloggers.
  • Physical hardware compromise of hardware tokens (YubiKey, Titan).
  • Cold-boot attacks or hardware RAM probing against active memory while the vault is unlocked.

No ES6 Classes

All components are built using pure factory functions. Errors are tagged plain Error objects with explicit code properties, making them transparent to serialize and audit.

Dependency Inversion

Zero ambient globals (process.env, Date.now(), raw networking). Every module receives its ports explicitly via arguments (createProxy({ ... })).

CI Structural Limits

CI enforces strict invariants: files must stay under 200 lines (codeStructure.test.js) and cross-module imports must only target index.js (moduleApi.test.js).

3. Zero-Knowledge Envelope Encryption & Storage Engine

Built with Libsodium (crypto_aead_xchacha20poly1305_ietf) following the zero-knowledge Bitwarden security model, without password-derived vault keys.

Layered Key Hierarchy

The master Vault Key is 32 cryptographically random bytes generated once. It is never derived from a password and exists strictly in RAM while unlocked.

Each passkey registered with Vaultgate derives a hardware-bound Key Encryption Key (KEK) using the WebAuthn PRF extension (hmac-secret). This KEK wraps its own copy of the Vault Key. Removing a passkey simply deletes its wrapped copy without requiring re-encryption of stored secrets.

Every individual record (secret, grant, or audit log entry) has its own independent 32-byte Item Key. Rotating or updating one secret touches only that single record.

EncString On-Disk Format

Encrypted fields follow: v1.<nonce_24b_base64>.<ciphertext_base64>. Even field names and record types are sealed in an encrypted schema manifest, concealing record types on disk.

Context-Bound AAD

Ciphertexts bind to strict context: AAD = recordId | fieldPos | recordVersion | v1. An attacker cannot move a ciphertext from a name field into a secret value field without instant MAC failure.

Anti-Rollback Header MAC

A keyed MAC over the storage header binds all public keys and a manifest of record versions: {recordId: version}. Reverting an individual record halts unlock with VAULT_TAMPERED.

4. Deterministic Decision Engine & Fail-Closed Rules

Requests pass sequentially down an unalterable evaluation table. The first matching rule decides the outcome. The rule name is returned in the response header (x-vault-gate-rule) and committed to the encrypted write-ahead audit log.

Write-Ahead Audit Logging & Fail-Closed Quarantine

To prevent untracked exfiltration, Vaultgate writes the decision to the encrypted audit log before decrypting any secret. If writing to the audit log fails (disk full or write lock), the request halts with audit-unavailable. After 3 consecutive audit failures, Vaultgate locks down the entire daemon process.

5. A Touch, Not a Click: Anti-Automation Defense & IPC

Why software confirmation dialogs are insecure against local scripts, and how hardware capacitive touch and secure IPC solve it.

The UI Automation Threat

Any local process running under the same user account (PowerShell, Python, UI Automation, SendKeys) can locate and click an "Allow" button on a standard desktop popup.

1.5s Anti-Click Delay

Tray confirmation popups disable actionable buttons for the first 1500 milliseconds upon appearance, thwarting rapid scripted event loops trying to intercept the window.

Mandatory FIDO2 Touch

"Allow once" permits strictly one request. Any durable grant (30 min, 4 hr, permanent, pairing a tool, or sensitive keys) requires a physical passkey touch. Malware cannot synthesize capacitive touch.

The Touch IPC & Challenge Protocol

The daemon and desktop tray communicate via a local socket / named pipe (src/tray-link/) secured by a one-time cryptographic token exchanged over stdin during startup. When high privilege is requested, Vaultgate initiates a touch challenge at /touch#<id> with a 256-bit one-time nonce and a 2-minute time-to-live. Users can enforce touchAuthenticator: external to require hardware USB/NFC tokens (e.g. YubiKey) over software PINs.

6. Handshake Verification & Multi-Alignment Scrubbing

Protecting outbound data before a single byte leaves, and cleaning inbound replies on the way back.

Strict TLS & TOFU Pinning

Vaultgate checks the TLS certificate chain during the handshake (via checkServerIdentity), before writing any request payload:

  • Validates against the OS certificate store (including corporate inspection roots).
  • Remembers leaf issuer and root fingerprint upon first verified connection (Trust On First Use).
  • If the certificate chain changes unexpectedly, the handshake aborts immediately with tls-chain-changed: not a single byte of plaintext leaves your machine.

Streaming Response Scrubber

Upstream APIs that reflect or echo headers cannot exfiltrate secrets back to the agent:

  • Scans outbound stream buffers in real-time as chunks arrive over the network.
  • Detects raw secret values, hexadecimal encodings, and all three possible base64 byte offsets.
  • Maintains sliding cross-chunk windows across TCP packets to eliminate edge-boundary leaks.

7. Agent Onboarding: RFC 8628 Device Flow

Autonomous AI tools and CLI assistants pair with Vaultgate using an RFC 8628 Device Authorization Flow adapted for local environments.

1. Request Pairing

The agent requests pairing via POST /device/code with its tool name. Vaultgate responds with an ephemeral verification code (e.g. ABCD-EFGH) and starts a 10-minute countdown.

2. User Verification

The user sees the visual code in their terminal and confirms it in the system tray or portal. Completing pairing mandates a physical passkey touch.

3. One-Time Issuance

Once verified, the agent polls POST /device/token and receives the virtual key vg_... exactly once. Vaultgate stores only a keyed HMAC in its registry.

8. Application & Deployment Integrity (Runtime & Supply-Chain)

Ensuring an autonomous agent executing in the same user session cannot silently alter Vaultgate's code or approval scripts to grant itself unauthorized access.

Startup Hash Verification

The cryptographic hashes of all runtime JavaScript modules and the tray script (windows-tray.ps1) are sealed with a key inside the encrypted vault.

If an agent alters any script, Vaultgate detects the discrepancy at startup, refuses to unlock (VAULT_TAMPERED), and displays a prominent red warning in the tray and portal.

Ed25519 Code Signatures

Builds bundle code into a single minified bundle (dist/vaultgate.cjs) signed with an Ed25519 private key in CI (dist/vaultgate.sig).

The bootstrap loader (bin/vaultgate.js) verifies the signature against a hardcoded public key using crypto.verify before loading code. Tampered bundles are rejected immediately (€0 cost).

Protected OS & Sigstore

Vaultgate installs into a system directory requiring UAC admin elevation to write, preventing regular user processes from modifying code.

Public packages (npx vaultgate) are released with Sigstore / GitHub Actions OIDC provenance (npm publish --provenance), linking binaries directly to public commits.

10. Security Auditor & Code Reviewer Checklist

Essential non-negotiable checks for any pull request or security review on the Vaultgate codebase.

1. Zero Plaintext Exposure

Secrets must reside in Node.js Buffer objects where possible and must never be converted to strings in logging or error formatting. All portal API routes must pass automated findLeaks assertions.

2. Mandatory Response Scrubbing

Every outbound response path emitting bytes to the client socket must pass through src/scrub/, scanning for raw values, hexadecimal encodings, and all 3 base64 offset alignments across chunk boundaries.

3. Fail-Closed Decisions

All decision branches in src/policy/ must default to deny. Every outcome must yield a standard discrete rule name mapped to the official decision table.

4. Write-Ahead Audit Log

Secret decryption must strictly follow audit log write confirmation. Missing or locked logs immediately halt the request with audit-unavailable.
